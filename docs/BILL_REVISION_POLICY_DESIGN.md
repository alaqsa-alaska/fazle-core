# Bill Revision Policy — Design Document (not implemented)

**Status:** Design only. No code, no migration, no schema change in this pass — per explicit instruction, this document exists specifically so that Completed-program editing and bill recalculation are NOT built until this policy is reviewed and approved. Nothing here has been applied.

**Context:** Phase 2B Commit C (`docs/CLIENT_DOMAIN_IMPLEMENTATION_PLAN.md`) built manual bill generation (`modules/client_billing/bills.py::generate_bill()`), writing to `wbom_billing_records`. The Owner separately decided (2026-07-10): "if a bill exists for a program and the program is later edited, the bill should be recalculated." Before building either the program-edit feature or the recalculation hook, this document works out what "recalculated" should actually mean once a bill may already have been paid, corrected, or referenced elsewhere.

---

## 1. Current state (what exists today)

- `wbom_billing_records` — one row per bill. Columns: `bill_id` (PK), `program_id` (**UNIQUE**, migration 036), `contact_id`, `bill_date`, `bill_number` (**UNIQUE**), `service_charge`, `other_charges`, `total_amount`, `payment_status` (**CHECK: `Pending`/`Paid` only**, migration 037), `payment_date`, `remarks`, `created_at`.
- `bill_number` format: `AQS-YYYY-NNNNNN`, generated by `next_invoice_number()` (migration 033) — a transactional counter, gapless within a rollback but **not reused** once issued (each call permanently advances the counter for that year).
- **No `updated_at` column.** No audit log table for bills exists (unlike `wbom_payroll_approval_log` for payroll).
- **No program-edit feature exists.** No route or admin command can currently modify a Completed escort program's core fields (`day_count`, dates, rate-relevant data) after creation — confirmed by code search. This is why recalculation has no hook point today.
- `payment_status` currently has exactly two states and no transition function yet (Commit D — mark-paid — is unbuilt). A bill is created as `Pending`; nothing currently moves it to `Paid`.

## 2. Governing principle

**A bill that has reached `Paid` is a historical financial record, not a mutable draft.** Real money has moved (or the business has recorded that it has) against that exact `bill_number` and `total_amount`. Editing a paid row in place — even to fix a genuine input error — destroys the ability to answer "what did we actually invoice/collect on this date," which is the one property an accounting record must never lose.

This gives two different correction paths depending on `payment_status` at the moment a correction is needed:

| State when correction is needed | Mechanism | Why |
|---|---|---|
| `Pending` | **In-place correction**, logged | Nothing has been collected yet; the bill is still a draft the client hasn't necessarily been charged against in an irreversible way. Editing it directly (with a mandatory audit-log entry) is simpler and doesn't fragment the client's invoice history. |
| `Paid` | **Reversal + replacement**, never in-place edit | The original row's amount and `bill_number` must stand permanently as issued. Correction happens by (a) recording a reversal against the original, and (b) issuing a brand-new bill with a new `bill_number` for the correct amount. |

This mirrors the pattern this codebase already uses elsewhere: `modules/payment_correction/__init__.py::adjust_payment()` never rewrites `fpe_cash_transactions` rows in place either — it creates a reversal transaction plus a new corrected transaction, preserving the original. The bill-revision design below is the same shape, applied to `wbom_billing_records`.

---

## 3. Pending-bill correction

- **Trigger:** an admin edits the underlying Completed program's billing-relevant fields (`day_count`, `end_date`/`end_shift` if duty_type-derived, or the admin re-runs bill generation with a different `duty_type`/`other_charges`) while the bill is still `Pending`.
- **Effect:** the existing `wbom_billing_records` row is updated in place — `service_charge`, `other_charges`, `total_amount` recalculated from the (corrected) program + the client's billing profile, `bill_number` and `bill_id` **unchanged**.
- **Mandatory:** every in-place correction writes one row to the new audit-log table (§5) capturing old values, new values, actor, and reason. This is not optional — an editable-while-pending bill without an audit trail would just move the "silent correction" problem instead of solving it.
- **Not allowed:** changing `contact_id` or `program_id` via this path (that would be re-billing a different program/client, not correcting a mistake — it should go through void + fresh `generate_bill()` instead).

## 4. Paid-bill correction (reversal + replacement)

Once `payment_status='Paid'`, a correction always produces **two new facts**, never a rewrite:

1. **Reversal record** — a row (new table, §5, or a `correction_type`/`reversed_bill_id` pair of columns on `wbom_billing_records` itself — open question, see §7) marking the original bill as reversed. The original row's `bill_number`, `total_amount`, and `payment_status='Paid'` are **never altered**. This mirrors `fazle_payment_drafts.correction_of` / `correction_type='reversal'`, the exact pattern `payment_correction` already uses for guard payments.
2. **Replacement bill** — a brand-new `wbom_billing_records` row, new `bill_number` (via `next_invoice_number()`, same as any fresh bill), correct `service_charge`/`total_amount`, `payment_status='Pending'` (it hasn't been paid yet — the client owes the corrected amount, or a refund/credit is owed if the correction reduces the amount, which is a separate operational step outside this table's scope).
3. The replacement bill references the original via a new `replaces_bill_id` column (§7) — this is how "invoice replacement" is represented: not a mutation, a documented chain (`bill A` → reversed → `bill B` replaces it), fully queryable.

**Net financial effect must be computable at all times** by summing non-reversed bills for a program/client — reversed bills stay in the table (for history) but are excluded from any "amount owed" or "amount billed this period" aggregate once flagged reversed.

## 5. Audit history

A new table is needed — no existing table can carry this. Proposed shape (design only, not applied):

```
wbom_billing_audit_log
    log_id          BIGSERIAL PRIMARY KEY
    bill_id         INTEGER NOT NULL REFERENCES wbom_billing_records(bill_id)
    action          VARCHAR(20) NOT NULL   -- 'created' | 'corrected_pending' | 'reversed' | 'replaced'
    actor            TEXT NOT NULL          -- admin identifier, matching wbom_payroll_approval_log's convention
    reason          TEXT
    old_values      JSONB                  -- null for 'created'
    new_values      JSONB                  -- null for 'reversed' (nothing "new" about the original row)
    related_bill_id INTEGER REFERENCES wbom_billing_records(bill_id)  -- the replacement, for a 'reversed' row; the original, for a 'replaced' row
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
```

This directly mirrors `wbom_payroll_approval_log`'s existing, already-proven shape (append-only, one row per state-changing action, JSON before/after) — no new pattern invented, just applied to bills.

## 6. Invoice numbering under replacement

- A replacement bill gets a **new, real** `bill_number` from `next_invoice_number()` — never a suffixed variant of the original (e.g., not `AQS-2026-000045-R1`). Reasoning: `next_invoice_number()`'s whole design point (migration 033) is a gapless, unambiguous yearly sequence; inventing a parallel suffix scheme reintroduces exactly the ambiguity that function exists to avoid, and a client-facing invoice document is clearer as "AQS-2026-000078 replaces AQS-2026-000045" (two real invoice numbers, explicit relationship) than as a suffix convention the client has to interpret.
- The original bill's `bill_number` is **never reissued or reused** — it stays permanently assigned to the (now-reversed) original row, exactly as a real accounting system would never let a voided invoice number be recycled.

## 7. Open design questions — need Owner sign-off before any of this is built

1. **Where does reversal/replacement metadata live?** Two options: (a) two new columns directly on `wbom_billing_records` (`reversed_at`, `replaces_bill_id`), simplest, matches how `fazle_payment_drafts.correction_of` already works; or (b) a dedicated join table if a bill could ever need multiple corrections over time (unlikely given "one bill per program," but worth deciding explicitly rather than assuming). **Recommendation: option (a)** — simpler, matches an existing in-codebase precedent, and the program_id-uniqueness constraint already limits how much correction chaining is realistically possible per program.
2. **Interaction with the `program_id` UNIQUE constraint (migration 036).** Today, one program can have at most one row in `wbom_billing_records`. A replacement bill for the *same program* would need a **second** row with the same `program_id` — which the current UNIQUE constraint forbids. This constraint needs to change to "at most one **non-reversed** bill per program" (a partial unique index: `UNIQUE (program_id) WHERE NOT reversed`), not removed outright — removing it entirely would reopen the original duplicate-billing risk migration 036 was built to close. **This is a real, concrete schema change that will be needed** once this policy is approved; flagged here, not applied.
3. **Who can reverse a paid bill?** Given the client-billing RBAC precedent just set (admin/superadmin only see rates/wages at all), reversing a *paid* bill is a strictly more sensitive action than viewing one. Recommend gating reversal at `superadmin` only, matching the delete-tier precedent already used for the client-billing-profile hard delete.
4. **Does a reversed/replaced bill need a distinct client-facing document (a formal credit note), or is the internal audit-log entry sufficient until Commit D's outstanding-balance/dashboard work exists?** Out of scope for this design pass — flagged for whoever builds Commit D.
5. **What happens to `payment_date` on a replacement bill once it too is eventually paid?** No special handling needed — it follows the same Pending→Paid path any fresh bill does; noted here only so it isn't assumed to inherit the original's `payment_date`.

## 8. What this document deliberately does NOT do

- It does not implement a program-edit feature (still doesn't exist).
- It does not implement the recalculation hook, the audit-log table, the new columns, or the partial-unique-index change described above.
- It does not change `wbom_billing_records`'s current schema in any way.

Building any of the above requires a separate, explicit go-ahead per item — this document exists to make that a specific, informed decision rather than an assumed one.
